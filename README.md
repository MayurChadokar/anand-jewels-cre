    # Anand Jewels CRE — standalone project

Independent FastAPI application extracted from the CRE module. It has its own
SQLAlchemy models/session, SQLite database, session authentication, templates,
requirements and server. `requirements.txt` lists direct dependencies;
`requirements.lock.txt` pins the complete validated Python 3.9 environment. It does not import or connect to the main backend.
Python 3.9 or newer is required. The included setup was checked with Python 3.9.

Store-based access and final database migration are specified in `STORE_BASED_ACCESS_IMPLEMENTATION.md`.

## Start on Windows PowerShell

```powershell
cd C:\syscraft\anand\anand-cre
py -3.9 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.lock.txt
.\.venv\Scripts\python.exe server.py
```

If `.venv` is already present, run the last command only. Open
http://127.0.0.1:8501/cre/login . Health: http://127.0.0.1:8501/health .
The main backend can continue on port 8000. For another port:
`python server.py --port 8002`. For development reload: `python server.py --reload`.

Deployment start command (port 8501):

```bash
python server.py --host 0.0.0.0 --port 8501
```

## Database and configuration

Default database: `data/cre.db`, resolved relative to this project, independent
of the shell's current directory. Copy `.env.example` to `.env` to override
configuration. This release uses SQLite; switching to PostgreSQL requires driver,
configuration and migration work. SQLAlchemy is installed in this project's own
virtual environment. No shared environment or source-code path is needed.

Session cookie: `anand_cre_session`, distinct from the main backend's cookie.
A private persistent secret is generated in `data/session.key` unless
`CRE_SECRET_KEY` is supplied. Use HTTPS and `CRE_COOKIE_SECURE=true` when hosting.
Do not commit `.env`, the database, migration reports, session key or logs.
Bootstrap, Bootstrap Icons and Google Fonts are loaded from CDNs as in the source UI.

## Existing data migration

```powershell
.\.venv\Scripts\python.exe migrate_from_main.py --source C:\syscraft\anand\anand-jeweller-backend\gold_rates.db
```

This command is only for an absent destination DB. It opens the source read-only,
uses SQLite's backup API to include committed WAL changes consistently, and copies
only these six tables: stores, admin_users, customer_product_types,
customer_form_fields, cre_staff_members, customer_visits. All store rows are copied.
Login users with super_admin/customer_relation_executive roles are copied, along
with any other historical users referenced by CRE records. Historical users with
other roles cannot log into this CRE application. Password hashes, primary keys,
foreign keys, timestamps and custom-field values are preserved. No plaintext
passwords are read or generated by migration. Existing CRE credentials continue to
work. Row checksums, counts, integrity and foreign keys are checked before publishing
the target. `data/cre.migration.json` records validation without customer details.
Migration refuses to overwrite an existing target or silently discard unknown columns.

The included migrated DB is a snapshot, not a live sync. New entries in either
project do not appear in the other. This extraction does not redirect or remove
CRE from the old backend. For a later production cutover, pause old CRE writes,
stop the new server, back up its data, and perform a final migration to a NEW
empty path before selecting the final database. Do not overwrite a database that
has received new CRE entries without reconciling those entries first.

## Final store-scoped database migration

When the final updated `cre.db` is available, migrate it into a new path. The
source is opened read-only, the destination must not exist, null historical
assignments use the explicitly confirmed existing-store ID, and optional user
or staff overrides can assign records to other stores.

```powershell
.\.venv\Scripts\python.exe migrate_store_database.py `
  --source C:\path\to\updated-cre.db `
  --destination C:\path\to\cre-store-scoped.db `
  --existing-store-id 1 `
  --user-store second_city_cre=2 `
  --staff-store 25=2
```

The command preserves all tables, refuses to overwrite a destination, validates
row counts, foreign keys and integrity, and writes a non-customer migration
report beside the new database.

Passwords are entered privately and confirmed. No default account or sample
business data is seeded automatically. Existing migrated accounts need no reset.
Stores and login accounts are administered with this CLI; sales people, managers,
products and form fields are administered through the CRE screens. Staff names
are not login accounts, matching the extracted module's existing behavior.

## Included features

## Walk-in feedback integration

Every new walk-in creates one unpredictable feedback token in the same database
transaction. The CRE Feedback screen is store-scoped and supports pending status,
submitted ratings/comments, read state, and resend with a two-minute cooldown.
Kit19 credentials and the Anand integration key must be supplied through the
environment; they are never rendered into HTML.

Feedback WhatsApp auto-send is enabled by default. Set
`FEEDBACK_AUTO_SEND=false` only when the deployment must temporarily pause
automatic messages. Manual resend remains an explicit admin action.

Automatic feedback delivery is durable and delayed. Each new walk-in stores a
`scheduled_at` value (five hours by default); it is not sent by the web request.
Run exactly one scheduler worker alongside the web application:

```bash
python -m scripts.feedback_worker
```

The worker checks every 30 seconds, sends each due Kit19 request individually,
recovers abandoned `processing` records, and retries provider failures after 5,
15, 30, and 60 minutes up to the configured attempt limit. Configure it with:

```dotenv
FEEDBACK_SEND_DELAY_HOURS=5
FEEDBACK_WORKER_INTERVAL_SECONDS=30
FEEDBACK_MAX_ATTEMPTS=5
FEEDBACK_PROCESSING_TIMEOUT_MINUTES=15
```

For a deployment smoke test, `python -m scripts.feedback_worker --once` processes
one due batch and exits. Because this release uses SQLite, deploy a single worker
process and configure the process manager to restart it on failure. Stop both the
web process and worker before taking a file-level `data/cre.db` backup. Run
`python manage.py init-db` once after deploying the code; migration 008 adds only
the scheduling columns and index and preserves existing feedback rows. Existing
unscheduled rows are not auto-sent. Rollback is: stop the worker, set
`FEEDBACK_AUTO_SEND=false`, and restore the verified pre-deployment database and
previous application version if a schema rollback is required.

The customer form loads customer, mobile number, and visit context from
`GET /api/feedback/{token}`, then submits JSON to `POST /api/feedback`. Anand
admin can mirror CRE records with `GET /api/integrations/feedback`, then use the
matching `/resend` and `/read` endpoints with an `X-Integration-Key` header. The
incremental cursor uses both `after_time` and `after_id`; persist it only after
the Anand mirror commit.

Customer forms, the dashboard and walk-in reports use one **Status** field:
Draft, Billed, Walkout, Old Gold, Repair Taken, Repair Delivered and Ordered
Delivered. Walkout requires a reason and remark, with an optional competitor.
The previous Purpose field is no longer shown. Existing New Jewellery drafts
display as Draft, and other historical purposes display as their status;
stored historical data is preserved.

Sales Person and Manager each offer **Not Assigned** in both Add and Edit forms.
Visits can be saved with either or both unassigned, then assigned later. These
visits also appear as Not Assigned in the dashboard and reports. Customer entry
requires a store and product, but does not require staff names to exist first.

Walkout reasons and competitor shops are managed from **Walkout & Competitors**
in the sidebar. Add choices or remove/restore them; removed choices remain on
existing visits and in report filters. Both CRE executives and super admins can
manage these lists, matching the existing product and staff permissions.

On startup, additive migration `001` in `visit_options.py` creates and initializes
the `cre_visit_options` configuration table. It imports the previous default
choices and existing visit values once per list. Subsequent starts preserve all
changes, including removed choices. The six business tables and historical visit
values are unchanged; migration from the main backend still copies only those
six source tables, with this local configuration initialized on server startup.

The sidebar opens a dedicated **Walkout Register** page at `/cre/walkout-register`,
showing visits from 1 January 2026 by default, a full-width register, and registered/current/recovered/
pending-follow-up metrics. Its Excel download contains one sheet with these exact
columns: Visit Number, Name, Mobile, Product Type, Category Type, Sales Person,
Meet by Manager, Walkout Reason, Status, Follow up 1, Follow up 2, Follow up 3.
Download filters match the page filters; recovered Billed visits stay included.
Search by customer name, mobile number, or visit reference such as `CRE-000105`.
Search also supports a numeric visit ID and stays applied during pagination,
follow-up edits, and Excel downloads. Clear search keeps the other filters.
While searching, date filters are ignored across the page and Excel export;
without search text, date filters apply normally.
The register's Edit popup permits only Status, Walkout Reason, and Competitor.
Customer identity, product/category, staff assignment, remarks, and follow-ups
remain unchanged by this edit. The latest reason/competitor are retained in
reports after billing; Billed entries remain locked.
Each visit has three sequential follow-ups: save a note once and it is
permanently locked, with its author and timestamp. Final status can change
from Walkout to Billed. Billed visits are permanently read-only, including
details, status, and new follow-ups. Recovered customers
remain in the register with the original walkout details, while report totals
use their current status. Excel exports include the register and all three notes.

Startup migration `002` in `walkout_followups.py` adds `cre_walkout_records` and
`cre_walkout_followups`, backfills existing Walkout visits, and installs database
triggers that reject follow-up updates/deletes. It is safe to run repeatedly.
Historical walkouts converted before this feature cannot be reconstructed if
their original walkout details were already cleared.

Products also manages the category dropdown. Add your category names there;
new visits require both a Product Type and Category. Existing visits keep an
unrecorded category until explicitly selected while editing an unbilled visit.
Migration `003` in `visit_categories.py` adds the category foreign key without
rewriting historical entries and installs database triggers protecting billed visits.

Each saved visit has a permanent reference such as `CRE-000105`, derived from
the database primary key. Database allocation keeps concurrent users' entries
distinct; no client calculates the next number. The reference is shown in the
dashboard, visit details, both report registers, and the Excel walkout register.
Search the dashboard using the full reference. S.No. remains the current list
position, so it can change with filtering and sorting. References do not reset
at midnight; the daily dashboard counts do. Numbers may have gaps.

Dashboard, report registers, competitor details, and manager/sales detail tables
default to 20 rows per page with numbered Previous/Next navigation. The
**Entries per page** dropdown offers 10, 20, 50, or 100 rows; click Apply after
choosing a size. Changing size resets pagination to page one and retains filters.
Each report table
has its own page parameter; filters are retained during navigation and reset
pagination when reapplied. Summary metrics and Excel downloads always cover the
entire filtered dataset.

CRE login/logout; dashboard/search/pagination; customer visit creation, editing
and billed/walkout statuses; sales people and managers; product types; dynamic
form fields including removal/restoration; report filters and Excel export.
The layout contains only CRE navigation, including when logged in as super_admin.
Gold/silver rates, queue, contact enquiries, public CMS and customer accounts are
not included. The legacy `/admin/customer-relations` bookmark redirects locally
to CRE; the main application's admin routes do not exist here.

## Verification and backup

Database queries, password verification, template rendering and Excel generation
run in FastAPI's worker threads so slow synchronous work does not block the event
loop. Request form bodies are parsed asynchronously before business work starts.
Gzip compression is enabled for clients that accept it, for responses above 1 KB.
Daily dashboard counts use one aggregate query, and dashboard rows preload stores.
Startup migration `004` in `query_indexes.py` adds composite indexes for date-based
status, sales-person, manager and store filters without rewriting existing data.
Reports and Excel downloads still cover the full filtered dataset; very large
exports can use significant memory. Concurrency tests cover a slow password check,
mixed dashboard/report requests and simultaneous visit creation. These checks do
not establish a production capacity limit; measure expected traffic on the host.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Tests use temporary databases and a separate temporary server port; they do not
change the delivered database. Tests exercise authentication, permissions,
customer workflows, filters/export and migration isolation/integrity.
Use SQLite's backup API for live backups; copying only `cre.db` while the server
is running can miss committed WAL changes. Back up the secret/config separately.
Schema creation is included; future schema changes need explicit versioned migrations.
Dependencies initially match the source stack; dependency upgrades are a separate task.
